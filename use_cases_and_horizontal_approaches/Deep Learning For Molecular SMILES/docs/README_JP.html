分子 SMILES のためのディープラーニング — DataRobot 上での学習とデプロイ

作成者: senkin.zhan@datarobot.com

サンプルデータ · ホールドアウトのテストセット — 目的変数 Tc を付与したポリマーの SMILES 文字列。

課題設定

SMILES（Simplified Molecular Input Line Entry System）は分子構造をテキストで表現したものです。姉妹アクセラレータである Feature engineering for molecular SMILES は、この文字列を表形式の特徴量（記述子、フィンガープリント、TF-IDF、学習済み埋め込み）へ変換し、DataRobot の Autopilot に渡します。

本アクセラレータはもう一方のアプローチを取ります。特徴量を事前に設計するのではなく、分子を直接読み込む PyTorch モデルで表現そのものを end-to-end に学習します。入力の扱い方は 2 通りあります。

  • 分子グラフ — RDKit で構築したグラフ上の DMPNN
  • 文字列シーケンス — SMILES トークナイザを通した LSTM / CNN / Transformer

重要なのは、学習とデプロイの両方が DataRobot 上で完結するという点です。独自のディープラーニングアーキテクチャは通常プラットフォームの外側に置かれ、別の場所で学習し、推論基盤を自前で用意することになります。本アクセラレータではライフサイクル全体が 1 か所に収まります。

  • DataRobot で学習 — ノートブックは DataRobot のコードスペースまたは DataRobot Notebooks でそのまま動作します。CPU でも GPU 環境でも構いません。
  • DataRobot でデプロイ — 学習済みの PyTorch モデルをカスタム推論モデルとしてパッケージ化し、モデルレジストリに登録してデプロイします。デプロイ後は他の DataRobot モデルと同様に、ガバナンス・監視の対象となり、標準の予測 API 経由でスコアリングできます。

アクセラレータの概要

すべては 1 つの設定ファイル config/config.yaml で制御されます。モデルアーキテクチャ、学習ハイパーパラメータ、そしてデプロイ時の計算リソースまで含まれます。model.type を dmpnn / lstm / cnn / transformer（lstm+cnn+transformer のように + で連結した組み合わせも可）に切り替えて再実行するだけで、コード変更は不要です。実行環境は DataRobot のコードスペースを推奨します。GPU 環境があれば学習は速くなりますが、必須ではありません。

train.ipynb                        deploy.ipynb                     predict.ipynb
─────────────                      ────────────                     ─────────────
input/*.csv  ──►  model/smiles_model.pth  ──►  Registry → Workshop  ──►  Deployment
  (データ)         src/**  ──►  deploy/model_lib.py   (カスタムモデル)      (バッチ推論)
                  (deploy.ipynb §3 で再生成)

本アクセラレータのワークフローは以下のとおりです。

  1. RDKit で SMILES を特徴量化します。化学的な意味を持つ原子・結合特徴を備えた PyTorch Geometric の分子グラフか、文字単位の SMILES トークナイザによるトークン列のいずれかです。
  2. 選択したアーキテクチャを 2 段階で学習します。まず train.csv の 20 % をホールドアウトして検証 MAE が最小となるエポックを特定し、次に学習データ全体でちょうどそのエポック数だけ再学習します。
  3. バンドル成果物を保存します。重みに加えて設定・原子マップ・トークナイザ語彙を同梱するため、推論時に学習用 CSV は不要で、語彙のズレも起こりません。
  4. src/ の推論に必要な部分を 1 つの deploy/model_lib.py にフラット化し、deploy/custom.py の DRUM フックと合わせてパッケージ化します。
  5. DataRobot のカスタムモデルワークショップへアップロードし、依存関係をビルドし、組み込みのカスタムモデルテストを実行してモデルバージョンを登録します。
  6. 設定から選ばれたリソースバンドル上に登録済みバージョンをデプロイし、ホールドアウトのテストセットをデプロイメント経由でスコアリングして、ローカルの予測値と照合します。

4. ステップ 1 — 学習（train.ipynb）

学習は 2 段階で行われます。input/test.csv には一切触れません。

  1. load_split(cfg) が input/{train,test}.csv を読み込み、続いて split_train_valid(train_df, cfg) が train.csv から 4:1 のホールドアウトを切り出します（data.valid_ratio、seed で再現可能）。
  2. 特徴量化器は train.csv のみから構築します。ホールドアウトの test.csv は原子種にも文字種にも寄与しません。推論時に未見の記号はゼロ one-hot / <UNK> になります。
    • グラフ系モデル → build_atom_map → smiles_to_graph
    • シーケンス系モデル → build_tokenizer → SMILESDataset
  3. ステージ 1 — run_train(...) が 80 % のサブ学習データで L1Loss、ホールドアウト MAE に対する ReduceLROnPlateau、早期終了を用いて学習します。戻り値にはホールドアウト MAE が最小となった best_epoch と lr_history が含まれます。チェックポイントは model/smiles_model_stage1.pth に書かれ、デプロイ用の成果物を上書きしません。
  4. ステージ 2 — run_train_full(...) が train.csv 全体を使ってゼロから best_epoch エポックだけ再学習します。lr_schedule= によりステージ 1 のエポックごとの学習率を再現します。検証セットがないため早期終了はなく、最終エポック時点の重みが model/smiles_model.pth に保存されます。

エポック数はそのまま引き継がれます。全体データはステージ 1 のサブ学習データより約 25 % 大きいため、ステージ 2 の 1 エポックあたりの勾配更新回数も約 25 % 増えます。

成果物は重みだけでなくバンドル

{
  "state_dict": ...,        # モデルの重み
  "cfg": ...,               # 学習に使った設定
  "target": "Tc",
  "smiles_col": "SMILES",
  "atom_map": {...},        # グラフ系モデル
  "tokenizer_vocab": {...}, # シーケンス系モデル
}

特徴量化器の状態が成果物の内部に同梱されるため、推論時に学習用 CSV は不要で、語彙のズレも原理的に起こりません。生成は trainer._build_bundle、読み込みは trainer.load_bundle が担当します。DRUM の fit フックもまったく同じ形式で書き出します。

DataRobot を介さずローカルで推論することも引き続き可能です。

from src.training.trainer import predict
preds = predict(["*CC(*)C(=O)c1ccc(C)cc1"], "model/smiles_model.pth")

5. ステップ 2 — デプロイ用バンドルの構築

DataRobot のカスタムモデルのアップロードではサブディレクトリが確実には保持されないため、src/** を 1 つのフラットなモジュールへ連結します。この処理は deploy.ipynb のセクション 3 で自動実行されるので、別途ビルドスクリプトを覚えておく必要はありません。

生成される deploy/model_lib.py は次のように作られます。

  • MODEL_LIB_SOURCES に列挙されたモジュールをトポロジカル順に連結する
  • すべてが 1 つの名前空間に入るため、パッケージ内 import（from .pooling import ...、from src... import ...）を除去する
  • 外部 import とクラス／関数の本体はそのまま保持する
  • 旧来の torch_scatter import を PyG ベースのフォールバックへ書き換える
  • 環境変数のプリアンブル（USER / HOME / TORCHINDUCTOR_CACHE_DIR）を先頭に付与する。DRUM コンテナは /etc/passwd にエントリのない uid で動作する一方、torch._dynamo は import 時に getpass.getuser() を呼ぶため

再生成されたファイルはアップロード前に構文チェックされます。DR_REBUILD_MODEL_LIB=0 を設定すると、既存の deploy/model_lib.py をそのままアップロードします。

deploy/ — アップロードされる一式:

ファイル 役割
custom.py DRUM フック: fit, load_model(code_dir), score(data, model)
model_lib.py 生成されたフラットライブラリ（約 70 KB）
model-metadata.yaml type: inference, targetType: regression, targetName: Tc
requirements.txt torch==2.12.1, rdkit, torch-geometric, PyYAML（numpy/pandas/sklearn はベースイメージに同梱。torch-scatter は意図的に除外 — §8 参照）

deploy/ に .pth は置きません。ノートブックは常に model/smiles_model.pth の最新版をアップロードし、その更新時刻を表示します。

成果物が dict 形式のバンドルであるため load_model を登録しています。これがないと DRUM 既定の .pth オートローダーが nn.Module として呼び出そうとして失敗します。score() は trainer._predict_with_bundle に委譲しており、コードスペースで使う推論経路とまったく同一です。

補足: ローカルで DRUM を試す

drum fit --code-dir . --input input/train.csv --target-type regression \
         --target Tc --output /tmp/drum_out

fit は train.ipynb と同じ分割（split_train_valid、seed 付き permutation、data.valid_ratio 既定 0.2 → 80/20）と、同じ 2 段階スケジュールを使います。ホールドアウトで best_epoch を求め、そのエポック数だけ全量を再学習し、ステージ 1 の学習率軌跡を再現します。デプロイ用バンドルは DRUM の出力ディレクトリへ smiles_model.pth として書き出されます。

セクション構成:

§ ステップ
1 接続（SDK バージョン、エンドポイント、アプリのルートを表示）
2 設定 — 名前、目的変数、計算リソースを config/config.yaml から読み込み、ステップの ON/OFF

5 ベース実行環境の選択（[DataRobot] Python 3.12 PyTorch Drop-In）

10 ワークショップの URL を表示
11 カスタムモデルテスト（ワークショップの Test タブと同じ検査）
12 レジストリへ登録 + デプロイ（再実行時はモデル置換）
13 最終確認 — デプロイメント経由の実予測と正解値との MAE

ステップの ON/OFF

既定値は config/config.yaml の deploy.steps から読み込まれ、実行時には環境変数（1/true/yes が ON）が優先されます。

変数 既定 0 にしたときの動作
DR_REBUILD_MODEL_LIB ON src/ から再生成せず、既存の deploy/model_lib.py をアップロード
DR_CREATE_NEW_VERSION ON 新バージョンを作らず、既存の最新バージョンを再利用
DR_BUILD_DEPENDENCIES ON 依存イメージのビルドをスキップ
DR_RUN_MODEL_TEST ON ワークショップのテストをスキップ
DR_REGISTER_AND_DEPLOY ON ワークショップまでで停止（登録・デプロイなし）
DR_RUN_PREDICTION_TEST ON 最後のスコアリング確認をスキップ 
# 一時的なネットワーク障害の後、新バージョンを重ねずに再開する
export DR_CREATE_NEW_VERSION=0     # その後 deploy.ipynb を実行

計算リソースの選択ロジック

instance: cpu → CPU バンドルのみ;  instance: gpu → GPU 付きバンドルのみ
絞り込み: cores >= cpu_cores かつ memory >= memory_gb かつ gpus >= gpu_count
選択:    残った中で最小のバンドル（候補はすべて表示）

cpu / 2 コア / 6 GB の場合は cpu.4xlarge（4XL: 2 コア, 6 GB）が選ばれます。条件を満たすものがなければ、利用可能な全バンドルを列挙したエラーになります。

バンドルは datarobot.models.resource_bundle.ResourceBundle.list() を "customModel" in use_cases で絞り込んで取得します。SDK の create_clean() には resource_bundle_id 引数がないため、ノートブックは CustomModelVersion._create(..., extra_upload_data=[("resourceBundleId", ...)]) 経由で渡し、この private API が変わった場合は create_clean + PATCH にフォールバックします。バンドルを明示しないと DataRobot は既定の cpu.medium（1 コア / 1 GB）を使いますが、これは torch + rdkit には小さすぎます。

冪等性

  • カスタムモデルは名前で検索して再利用します。
  • 再実行時は、ラベルで一致した既存デプロイメントに対してモデル置換を行い、2 つ目のデプロイメントは作りません。
  • ビルド済みの依存イメージは検出され、再ビルドされません。

7. ステップ 4 — 予測（predict.ipynb）

デプロイメント経由でスコアリングするため、torch / rdkit / src.training は不要で、DataRobot SDK だけで動きます。

§ ステップ
1 接続
2 config/config.yaml から設定を読み込み（target, data.smiles_column, deploy.model_name）
3 接続中のクラスタ上でデプロイメントを解決（ID ヒント → ラベル検索）し、ラベル / ステータス / モデル / コンソール URL を表示

既定値は config/config.yaml の predict: ブロック（scoring_csv, row_limit）から読み込まれ、実行時には DR_SCORING_CSV / DR_DEPLOYMENT_ID が優先されます。

クラスタ非依存な設計。 デプロイメントはラベル（deploy.model_name、既定は smiles_deep_learning_regression）で識別されます。このラベルは deploy.ipynb がデプロイメント作成時に設定します。deploy.deployment_id は検索を省くためのキャッシュにすぎません。ID はクラスタ固有なので、app.datarobot.com で得た値は app.jp.datarobot.com では解決できませんが、その場合ノートブックはエラーにせず黙ってラベル検索へフォールバックします。接続中のクラスタにそのラベルを持つデプロイメントが 1 つもない場合にのみ停止し、先に deploy.ipynb をそのクラスタで実行するよう促します。

8. DataRobot Notebooks で学習する場合

本フォルダは自己完結しています（config/, input/, src/, train.ipynb, predict.ipynb, deploy.ipynb, deploy/）。DataRobot の Notebook セッションへアップロードするか、コードスペースで開いて train.ipynb を実行するだけで、他の準備は不要です。

同じコードをローカルでも DataRobot でも動かすために、移植性に関する対応を 2 点入れています。

  1. torch_scatter は任意であり、requirements.txt からはインストールできません。 src/models/_scatter.py が 3 段階のフォールバック付きで scatter_add を提供します — torch_scatter → torch_geometric.utils.scatter(reduce="sum") → 純 torch の scatter_add_。ビルドが一致しない torch_scatter ホイールは _scatter_cuda.so の読み込み時に ImportError ではなく OSError を送出するため、両方を捕捉しています。参照実装と数値的に一致することを確認済みです。

    DataRobot の依存関係マネージャは requirements.txt を独自に解析し、パッケージ名 + バージョン制約の行しか受け付けません。--find-links の行があるとビルドが 422 ... does not contain a valid package name for python で失敗します。torch-scatter は PyPI にホイールが存在せず（sdist のみ）、ビルド済みホイールはまさにその参照できないインデックス上にあるため、このファイルからは完全に除外しています。コンパイル済みの高速パスがどうしても必要な場合は、依存関係マネージャではなくカスタム環境（任意の pip オプションが使える Dockerfile）を構築してください。

  2. ReduceLROnPlateau に verbose= を渡さない。 この引数は torch 2.2 で非推奨となり、その後削除されました（DataRobot Notebooks では TypeError）。現在の trainer.py は scheduler.step() の前後で学習率を比較し、LR reduced: ... -> ... を自前で出力します。
